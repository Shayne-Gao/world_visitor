# 世界迷雾 / Fog Visitor 项目基线

## 1. 项目是什么

这是一个 **Android APK 优先** 的个人地理足迹记录产品。

目标不是做一次性的定位 Demo，而是做一套：
- 本地优先（Local-First）
- 可长期运行
- 可长期积累
- 可持续记录个人地理资产

的“世界迷雾”系统。

用户通过：
- 自动记录
- 手动定位
- 手动标记

持续点亮自己走过的地图区域，逐步形成长期可沉淀、可导出、可迁移的个人地理空间资产。

## 2. 产品边界

- 当前主线是 **Android APK**
- 根目录 `index.html` 是旧 Web 原型，默认视为封版
- APK 实际运行界面是 `apk/app/src/main/assets/web/index.html`
- 当前架构是 **原生 Android 外壳 + WebView 地图界面 + 原生单一数据真相**

## 3. 核心技术结构

### 3.1 原生侧

- `MainActivity.kt`
  - WebView 宿主
  - 权限申请
  - 原生状态轮询
  - 启动定位服务
  - 原生与页面同步桥接
- `TrackingForegroundService.kt`
  - 自动记录主入口
  - 前台定位服务
  - 持续收点、过滤、checkpoint
- `NativeTrackStore.kt`
  - 原生单一数据真相
  - draft point / track segment 管理
  - 统一落段判定
  - 去重、合并、探索网格索引
- `storage/*`
  - Room 数据库
- `BootReceiver.kt`
  - 开机恢复 / 升级后恢复

### 3.2 WebView 侧

- `apk/app/src/main/assets/web/index.html`
  - 地图展示
  - 图层渲染
  - 手动交互
  - 本地缓存
  - 调试浮窗

### 3.3 核心依赖

原生依赖：
- AndroidX Core / AppCompat / Material
- AndroidX WebKit
- AndroidX Lifecycle Service
- Room
- Google Play Services Location

前端依赖（本地 vendored）：
- Leaflet
- Turf.js
- localForage
- Font Awesome

## 4. 当前数据语义

当前项目不是“来一个点就存一个点”的简单模型，而是：

1. 原生服务持续收定位回调
2. 通过精度 / 距离 / 静止过滤
3. 写入 draft points
4. 达到 checkpoint 条件后尝试形成候选轨迹段
5. 候选段统一经过 `NativeTrackStore` 的底层落段入口
6. 根据“是否新增探索区域”“是否需要并入上一段”等规则决定：
   - 落正式段
   - 合并到上一段
   - 直接拒绝

这意味着：
- 自动记录
- 手动定位
- 手动标记

最终都应该汇合到一致的数据语义，而不是各自维护不同的落库规则。

## 5. 产品优先级

这里的优先级不是“功能菜单优先级”，而是“产品是否可信、是否可长期使用”的优先级。

### 5.1 P0：必须可靠成立

#### P0-1 自动记录必须真的工作

- 开启自动记录后，实际移动时必须持续取点、持续推进数据状态
- 不允许出现“显示在记录，但点不动、段不涨”
- 步行、开车、前后台切换、锁屏后恢复都属于这一条的实际范围

#### P0-2 数据绝不丢失、绝不损坏

- 本地存储必须是可信单一真相
- 不能因为崩溃、异常中断、恢复逻辑错误导致数据损坏或丢失
- 长期积累类产品，数据可靠性是根基

#### P0-3 数据语义正确

- 原地不动不能疯狂涨段
- 点一次定位不能莫名加多段
- 已探索区域不能重复生成无意义重叠数据
- 手动标记不能污染真实蓝点和最近定位状态

#### P0-4 后台 / 锁屏 / 重启后的记录连续性

- 前台服务必须稳定
- 后台记录不能轻易断
- 开机恢复、升级恢复、自恢复链路必须可靠

#### P0-5 打开 App 就进入当前态

- 打开 App 后应尽快看到当前所在位置
- 蓝点不应依赖手点“定位”才出现
- 地图中心不应停留在默认或历史缓存位置
- 自动记录状态、蓝点、地图视角必须一致

#### P0-6 导入 / 导出必须可靠

- 用户的地理资产必须可以导出
- 导入不能破坏原有数据语义
- 导入 / 导出是“长期资产可迁移、可备份”的基础能力，不是可有可无的附属功能

#### P0-7 地图坐标体验必须正确

- 地图显示位置必须和用户真实位置一致
- 蓝点、轨迹、底图之间不能明显错位
- 坐标系处理和地图对齐是地理产品的基础真实性要求

#### P0-8 不会带来数据爆炸

- 记录 1 小时不能膨胀成不可接受的大体积数据
- 必须具备有效压缩、有效合并、有效去噪能力
- 同时不能为了压缩而过度损失真实轨迹语义
- “有效压缩”和“不要过度压缩”必须同时成立

### 5.2 P1：重要体验增强

#### P1-1 启动速度

- 命中本地缓存时应尽量快开
- 不应长时间卡在“准备数据”

#### P1-2 状态可见与调试可见

- 用户能看懂当前是否在记录
- 用户能看懂为什么没写入
- 必要时能在 UI 中直接看到关键链路日志

#### P1-3 手动标记体验

- 交互顺手
- 不阻塞
- 不和自动记录互相污染

#### P1-4 长时间续航与使用舒适度

- 省电
- 夜间 / OLED 友好
- 浮窗、按钮、地图交互不打架

## 6. 当前用户最核心的痛苦

当前用户最强烈的痛苦，不是“想要更多功能”，而是“基础能力必须可信”。

主要集中在：

1. 自动记录不稳定
   - 看起来在记录，实际上不推进
2. 打开 App 后不在当前位置
   - 需要手动点定位，体验割裂
3. 启动慢
   - 命中缓存后仍卡住
4. 数据语义不稳
   - 涨段异常、重复数据、重叠数据
5. 用户对修复信任度下降
   - 不接受“看起来像修了”
   - 必须能用证据证明当前链路真的成立

## 7. 当前开发和发布纪律

### 7.1 不可违反的规则

- 先解决真实问题，不引入回归
- 已确认问题直接修，不做多余确认
- 不允许忘记版本号
- 不允许只改代码不出 APK
- 不允许只说结论、不留下文档和可验证证据

### 7.2 每次发布必须同步更新

- `apk/app/build.gradle.kts`
- `apk/app/src/main/assets/web/index.html`
- `README.md`
- 固定 APK 发布产物：
  - `apk/releases/latest/fog-visitor-debug-latest.apk`

## 8. 当前接管结论

从项目目标和现状看，当前最重要的不是继续扩功能，而是把以下几条打牢：

1. 自动记录真的工作
2. 打开即在当前位置
3. 数据语义稳定、不爆炸
4. 导入导出可靠
5. 地图坐标体验可信

后续所有开发都应围绕这几个 P0 展开，而不是被零散表象问题牵着走。
