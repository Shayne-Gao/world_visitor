# Changelog - 世界迷雾 (Fog Visitor)

当前仓库同时保留旧 Web 原型与 Android APK 主线；自 `v0.1.41` 起，变更记录默认以 **Android APK + WebView 壳 + 原生单一真相** 为主。

本项目旨在打造一个**完全本地优先 (Local-First)**、可终生记录并运行 30 年的个人地理空间数字资产系统。

项目基线文档见：`docs/PROJECT_BASELINE.md`

## 未实现需求池

### 断档推断线（暂不实现）

#### 背景
* 当前 `v0.1.88` 已实现：**超过 120 秒没有新的有效点，就自动断轨并从当前点重新开始**。
* 这样可以避免把长时间失联后的两个点硬连成一条正式轨迹，但也意味着“断档前最后一个点”和“断档后第一个点”之间不会再有任何连接展示。

#### 需求描述
* 增加一种**断档推断线**能力，用于表达“两个正式轨迹段之间存在一次跨段移动关系”，但**不把这条连接误当成真实连续采样轨迹**。
* 典型场景：
  * 上飞机前最后一个有效点在北京
  * 中间长时间无有效采样
  * 落地后第一个有效点在新加坡
  * 正式轨迹不应把北京和新加坡直接连成一条真实轨迹，但用户可能希望在地图上可选看到“这两段之间发生过一次跨段移动”

#### 技术方案草案
* 触发时机：
  * 当自动追踪因为“断档超过 120 秒”而执行断轨时
  * 记录断档前最后一个有效点 `A`
  * 记录断档后恢复的第一个有效点 `B`
  * 生成一条 `A -> B` 的推断连接
* 数据语义：
  * 推断线不是正式轨迹
  * 推断线不代表中间真实路径就是直线
  * 推断线只表示“断档前后存在一次跨段移动关系”
* 存储建议：
  * 单独定义推断线数据类型，避免混入正式 `track_segments`
  * 不建议仅在运行时临时拼装，否则导入导出、重启恢复、一致性都会比较差
* 展示建议：
  * 地图上单独图层显示
  * 默认关闭
  * 用户通过筛选开关手动显示
  * 样式上应与正式轨迹明显区分，例如虚线、低饱和颜色
* 与正式轨迹的关系：
  * 正式轨迹继续按真实连续采样数据落库
  * 推断线只做辅助表达，不篡改正式轨迹语义

#### 明确不参与的内容
* 不参与探索面积计算
* 不参与迷雾解锁
* 不参与国家 / 城市 / 区探索度统计
* 不参与正式轨迹长度统计
* 不参与 timeline 正式轨迹回放

#### 复杂度评估
* 这是一个**明确会增加系统复杂度**的功能，不是简单加一条虚线：
  * 需要单独的数据类型或存储结构
  * 需要单独的渲染图层和显示开关
  * 需要在统计、面积、导入导出、筛选逻辑里明确排除
  * 需要在产品语义上持续向用户说明“推断线不是正式轨迹”

#### 当前决策
* **暂不实现**
* 当前先以“120 秒断档自动断轨”为正式行为，保持正式轨迹语义干净
* 如果未来确实需要表达断档前后的跨段移动关系，再按本方案作为单独的可选辅助图层实现

## [v0.1.98] - 2026-08-05
### ⚡ Native Cache Hydration Optimization (原生缓存同步优化)
* **减少不必要全量重建**：APK 启动时 Native 比 Web 缓存新增轨迹的增量阈值从 50 提升到 1000，类似 364 条新增轨迹会走增量补齐，不再直接触发全量 hydration。
* **全量重建恢复每日缓存**：原生存档全量 hydration / normalize 时同步重建 `dailyExplored`，避免重建后 `dailyKeys=0` 导致时光机数据缺失。
* **历史坏缓存自修复**：如果 Native 与 Web 轨迹数已一致但本地 `dailyExplored` 为空，会触发一次修复性 progressive hydration，修复后后续启动应命中缓存。
* **渐进式全量 hydration**：启动后的全量 hydration 改为 progressive rebuild，过程中分批让出主线程，降低长时间卡死感。

## [v0.1.91] - 2026-07-28
### ⚡ Cold Start Incremental Catch-up (冷启动增量补齐)
* **冷启动缓存少量落后时不再整份 hydration**：如果本地可渲染缓存有效、原生 truth 只新增少量轨迹，启动后会按本地最新时间戳拉取新增轨迹并增量补齐，不再直接对整份 archive 重建地图数据。
* **统一增量阈值为 50 条轨迹**：前台恢复和冷启动补齐都使用同一个 `50` 条阈值；只有新增超过阈值、缓存不可用或增量失败时才回退整份 hydration。

* **自动追踪“防飞线”机制 (Anti-Flying-Line)**：彻底修复了移动端锁屏、切后台导致 GPS 中断后，重新唤醒时与上一个坐标连成穿墙长直线（飞线）的致命 Bug。
  * **机制原理**：当系统检测到两个连续坐标点之间的距离突变 `> 200米` 时，会自动判定为“断线”。此时系统会静默结算（保存）中断前的上一段轨迹，并将当前的新坐标作为一段全新轨迹的起点。
  * **效果**：保证了真实足迹的绝对可靠性，宁可留白也绝不瞎连直线。

## [v0.1.13] - 2026-03-26

* **数据结构 v2.0.0 正式发布**：

## [v0.0.9] 及更早版本 (MVP 概念验证期)
### 🚀 核心奠基
* **引擎选型**：确立以 `Leaflet.js` 为渲染底座（卫星图/街道图无缝切换），以 `Turf.js` 为空间几何运算核心。
* **迷雾消除逻辑**：实现核心的 `turf.difference`（全局迷雾挖洞）与 `turf.union`（足迹融合）布尔运算。
* **实时定位打卡**：接入浏览器原生 `Geolocation API`，支持基于当前 GPS 坐标的实时点亮。
* **基础交互**：实装多档位画笔 (`0.02km / 0.05km / 0.1km`)，支持单指划线、撤销操作。
* **历史回溯系统**：引入按天记录的“时光机”滑块，可回放过往的解锁足迹。
* **极限数据瘦身**：在 LocalStorage 时期，采用 `turf.simplify` (抽稀) 和 `turf.truncate` (截断小数位) 的极限容灾策略，防止存储过早溢出。
